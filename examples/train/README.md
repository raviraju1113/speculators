# DSpark speculative-decoding drafts for `google/gemma-4-31B-it`

Everything about the Gemma-4-31B DSpark draft models trained in this fork:
the data, the two architectures we settled on (all-sliding DSpark, and the
same plus the DFlash2 local convolution), the checkpoints, how each was
evaluated, the numbers, and how to run the scripts. Deeper material:
`HANDOFF.md` (machines, environments, gotchas), `notes/` (working notes),
`.claude/skills/` (`dspark-gemma4-handoff`, `dspark-train-serve-parity`,
`draft-opd`), `DSPARK_GEMMA4_RUNBOOK.md` (cluster era).

**Status (2026-10-26).** Checkpoint to deploy: **block-12 ep33**
(`gemma4_31b_dspark_nemo782k_conv_blk12/checkpoints/33`, served at k=12), or
**conv ep25** (`gemma4_31b_dspark_nemo782k_conv/checkpoints/25`) where the
server runs k=8 — at k≤8 the two are equal. Conv ep25 on B200 at k=8 decodes
5.5× / 3.8× / 4.5× faster than the target alone on AIME / GPQA / LiveCodeBench
and beats Google's native `gemma-4-31B-it-assistant` draft on throughput on all
three (+33% / +7% / +21%); k=12 adds +7…+16% tok/s on top (A100 so far). It
trails the assistant on GPQA acceptance (vocab gap, §6). Next stage:
Draft-OPD post-training seeded from block-12 ep33 (§0, §8).

## 0. What works so far — the current recipe

The recipe is cumulative: each stage keeps everything from the one before and
changes one thing. "Works" means it beat the previous stage on the standard
eval (§6.1) at matched k, with no loss elsewhere.

| stage | change | result | status |
|---|---|---|---|
| **1. Data** (§1) | nemo782k: 782k conversations, Gemma-4-31B-it responses, kimi-mtp + Nemotron STEM/math/code | the only SFT corpus used; GPQA is where it is thinnest (science 12%) | fixed |
| **2. Recipe A** (§3) | all-sliding DSpark (5 layers, window 2048, block 8, 32k draft vocab, CE+TV loss), 26 epochs from scratch | the baseline: scratch ep25, val 4.71 | superseded by B |
| **3. Recipe B** (§4) | A + DFlash2 local convolution (kernel 2, group 16); same data and schedule; selector/KL loss **not** adopted | +0.1 accept_len at k=8, +0.1…0.2 on AA-LCR at every length to 112k; beats the Google assistant draft on tok/s at k=8 on B200 | **works** → conv ep25 |
| **4. Block 12 by warm start** (§4.1) | B's ep25 checkpoint + 8 epochs at block 12, γ 12, nothing else changed | k≤8 identical to conv ep25 (nothing lost); k=12 over k=8: +7…+16% tok/s on A100, +6…+16% on B200 (395 / 254 / 313 tok/s on AIME / GPQA / LCB, §6.5) | **works** → blk12 ep33 at k=12 (block-8 control closed 2026-10-29: 8 more epochs at block 8 == conv ep25 on every benchmark at k=8 and k=5, §6.3b — the draft had converged, the k=12 gain is from the new slots) |
| **5. Draft-OPD** (§6.5, §8, **`opd/README.md`** — summary, paper diff, what worked, next steps; log in `opd/PLAN.md`) | on-policy post-training of stage 4's checkpoint on its own rollouts (acceptance-aware loss: forward KL on accepted slots, 0.05 × reverse KL on the first rejected slot, out-of-vocab rejected slots masked) | full run v2 (8 rounds × 16k external science/chat prompts): paired rollout acceptance on the pool up every round, 0.212 → 0.257 (+22%) — but on the standard benchmarks accept_len fell 9–18% at k=12 and 7–15% at k=8 (§6.5): the draft learned the pool and forgot math/code | **not adopted** (2026-10-28) — fails the bar below; next try needs a benchmark-domain pool and/or SFT replay |

**Current working recipe** = stages 1–4: train recipe B for 26 epochs on
nemo782k, warm-start 8 more epochs at block 12 / γ 12, serve
`conv_blk12/checkpoints/33` at k=12 (k=8 where the server cannot schedule
12-slot blocks; see §6.3b for the vLLM flags k=12 needs). Draft-OPD is being
run on top of exactly this checkpoint (`opd/run_rounds.sh` defaults: seed
blk12 ep33, k = block = γ = 12).

Tried and not kept: the DFlash2 selector/KL loss (§4, parity and simplicity
over an untested gain); OPD at the paper's LR 3e-4 (destroyed the draft),
OPD with fully-accepted blocks dropped (worse: they carry the anchoring
signal), OPD with the paper's full-weight reverse KL on the rejected slot
(acceptance fell every round: 28% of those slots point at a token outside
the 32k draft vocab and the term is ~200× the accepted one), and forward KL
on the rejected slot (worse than reverse at the same weight); a from-scratch
block-12 run (5.5 days for an answer the warm start gave in 2).

## 1. Dataset

Both corpora are **on-policy**: every assistant turn was generated by the
target, `gemma-4-31B-it`, from an existing prompt set; the original answers
were discarded. **Sampled, not greedy** (corrected 2026-10-27): the regen
client sent no temperature and the server log
(`kimi-regen-gemma4-31b/vllm_gpu0.log`) shows vLLM applied gemma's
generation_config — temperature 1.0, top_k 64, top_p 0.95; the earlier
"greedy" note came from a tutorial's pseudocode, not from the run. Verified 2026-10-12 by hashing prompts/answers across
shards (`notes/gemma4-dspark-data-provenance.md`). All rows are single-turn
user → assistant, no system prompt, no `<think>` traces.

| corpus | rows | prompts | regeneration | used by |
|---|---|---|---|---|
| **kimi-regen 349k** | 349,138 | kimi-mtp-dataset | chenw, `kimi-regen-gemma4-31b/train_regen.jsonl` (8-GPU multi-hour job) | first runs (`accum23x4`, `anchorT`) |
| **kimi + nemotron 782k** (`kimi_nemotron_782k`) | 782,413 | ~291k kimi-mtp (273k byte-identical to the above) + ~491k Nemotron-Post-Training-v2 **stem / math / code** | Ravi, 2026-07-30..08-01 | every run from `anchorT_nemo782k` on: scratch, fullattn1/2, conv, block-12 |

Composition of the 782k set (30k-row sample, keyword heuristics,
2026-10-22): math-like 54%, multiple-choice format 45%, code 11%, **science
(chemistry/physics/biology) ~12%**, other 12%; median answer ~1.7k chars.
The science share matters for the GPQA gap (§6).

Preparation: `scripts/prepare_data.py --model <gemma-4-31B-it> --data
<jsonl> --seq-length 8192 --output <dir>` writes the arrow shards
(`input_ids`, `loss_mask` over the assistant span, `seq_len`, `messages`,
torch-formatted) plus `token_freq.pt`; the first training run derives the
**32k draft vocabulary** (`d2t.npy` / `t2d.npy`: the 32,000 most frequent
target tokens). **A checkpoint is bound to the mapping it was trained with**:
any dataset used with it (continuations, OPD rounds, ablation "controls") must
carry the same `d2t/t2d` files — the trainer silently rebuilds a *different*
mapping from `token_freq.pt` otherwise, and the draft reads as garbage (slot-0
accuracy 0.00; cost us two pilot runs, see `opd/PLAN.md`).

Locations: lax01 `/sms-scratch/mengmengj/data/{gemma4_dspark,kimi_nemotron_782k}`;
sc3 `/import/ml-sc-scratch1/mengmengj/datasets/kimi_nemotron_782k` (symlinks
resolved). Target model: `/sms-scratch/checkpoints/gemma-4-31B-it` /
`/import/ml-sc-scratch5/chenw/models/gemma-4-31B-it` (needs its
`chat_template.jinja` at serve time).

## 2. Draft architecture (shared by all runs)

DSpark = a DFlash-style parallel block drafter plus intra-block dependency
heads (DeepSeek, arXiv:2607.05147; implementation upstream in
`vllm-project/speculators`, PR #677). Ours, matching RedHat's shipped
`gemma-4-31B-it-speculator.dspark` where it has a say:

| | |
|---|---|
| backbone | 5 Qwen3-style decoder layers (`transformer_layer_config.model_type: qwen3`), hidden 5376, 32 heads / 16 KV heads, head_dim 256, **all layers sliding-window attention, window 2048**, no full-attention layers |
| target features | aux hidden states from verifier layers **1 / 17 / 29 / 47 / 58** + last layer, fused by `fc` (5×5376 → 5376); the draft never sees the raw context tokens, only these |
| block | `block_size 8`, `sample_from_anchor=True` (slot 0 is the anchor's own prediction → k=8 native; k is a serve-time knob, we also serve k=5/3) |
| heads | Markov head (rank 256, `vanilla`) adds a previous-token transition bias at sampling; confidence head (trained, labels = 1 − TV, not served yet) |
| vocab | draft vocab 32,000 (`d2t/t2d`), mask token id 4 |
| params | ~2.4B trainable (+72.5M with the convs, §4) |
| loss | `0.1·CE + 0.9·TV` on the draft-vocab support + `1.0·BCE(confidence)`, per-slot weight `exp(−(k−1)/γ)`, γ = 4 (DeepSpec's value) |

**Why all-sliding.** We trained variants with one or two full-attention draft
layers (`fullattn1`, `fullattn2`): identical in-window, but on the AA-LCR
long-context bins they decay to ~3.0 accept_len at 112k while the all-sliding
draft stays flat at ~4.0 (§6.3). Cause: the draft's full layers run the local
θ=10k RoPE on contexts they never trained on, whereas the global context
already arrives pre-integrated in the target's fused hidden states (aux
layers 17/29/47 are Gemma's full-attention layers). Serve-time YaRN on the
full layers recovers most of it, but all-sliding needs no patch and is what
RedHat ships. Decision recorded 2026-09; `notes/dspark-results-status.md`.

**Serving note (`sample_from_anchor=True`).** vLLM 0.26.0 hard-codes the
opposite layout for speculators-format DSpark checkpoints and decodes such a
draft one slot off — loads cleanly, reports ~half the real acceptance
(1.84 vs 3.57 measured on identical weights). All our serving environments
carry `vllm_patches/algos.patch` (`dspark_bonus_anchor = not
sample_from_anchor`); upstream vLLM main derives it from the config.
Skill: `dspark-train-serve-parity`.

## 3. Training recipe A — all-sliding DSpark from scratch

Preset `run_nemo782k_scratch_local.sh` (lax01) / the same env block in
`sbatch_sc3_nemo782k_conv.sh` minus the conv flags (sc3). Driver:
`dspark_online_gemma4_31b.sh` — **online** training: vLLM serves the target
with the hidden-state connector (4 DP engines, TP=1) and streams the aux
hidden states for each packed sequence while 4 training ranks (FSDP, torchrun)
consume them; hidden states are transient (`--on-generate delete`, ~64 KB/token
is far too much to cache for 782k rows).

| knob | value | why |
|---|---|---|
| data / split | nemo782k, `TRAIN_DATA_RATIO 0.998` | validation regenerates hidden states, so keep it small |
| sequences | packed to 8192 tokens, `MAX_ANCHORS 512` per packed sequence | 3072 (upstream default) OOMs the loss (`[anchors×block, 32k]` logits) |
| batch | `ACCUM_STEPS 18` × 4 ranks ≈ 7.4 conv/step × 72 ≈ **512 conversations per optimizer step** | DeepSpec's global batch; `train_accum.py` adds accumulation without touching the trainer |
| optimizer | Muon (2-D weights, 10× LR) + AdamW, weight decay 0, grad-clip 1.0 | upstream default |
| schedule | lr **6e-4**, linear decay, 4% warmup, `SCHED_TOTAL` = optimizer steps of the whole trajectory (26 ep × ~1,490 = **38,700**) | the schedule is sized in optimizer steps, so it must be given explicitly whenever data or epochs change |
| epochs | 26 (first 16, then a warm-restart extension to 26 — hence the LR climb/dip at epoch 16 in wandb `nemoscratch782k`) | the conv run used the clean 26-epoch schedule from step 0 |
| saves | every ¼ epoch into the same `checkpoints/<epoch>/` (13 GB each), `SAVE_BEST 0` | `--save-best` disables sub-epoch saving |
| wall time | 132 h on 8×B200 (lax01), 91 micro-steps/min | |

Result: `gemma4_31b_dspark_nemo782k_scratch/checkpoints/25` (= `checkpoint_best`),
val accept_len **4.711**. This is the control for every architecture ablation.

## 4. Training recipe B — all-sliding DSpark + DFlash2 local convolution

**What DFlash2 is** (z-lab / inco.ai, Aug 2026; upstream speculators #1006,
`src/speculators/models/dflash2/`): DFlash plus (a) a two-tap **grouped
dynamic causal convolution** wrapping attention and MLP in every draft layer
(`conv_kernel_size 2`, `conv_group_size 16`, taps along the block axis, never
crossing an anchor block, identity-initialized), (b) a **candidate selector**
(top-16 unary candidates per slot, bilinear predecessor/successor codebooks
rank 256, sequential walk in a Triton kernel) with its own selector loss,
(c) a `kl_div` default loss and a `sliding_window_non_causal` option. Their
ablation (Qwen3.5-4B): selector alone +0.34/+0.47 accept_len, conv alone
"close to a 15-layer DFlash", both 4.92 → 5.97.

**What we took: the convolution only**, as an option on the DSpark model
(`DSparkSpeculatorConfig.conv_kernel_size/conv_group_size`, 0 = off; CLI
`--dspark-conv-kernel-size 2 --dspark-conv-group-size 16`;
`speculators_model_type` stays `dspark`; commit `034b0fc`). Two convs per
layer × 5 layers = 10 modules, +72.5M params. **What we left out and why**
(`notes/dflash2-port-assessment.md`, 2026-09-23):

- *Selector*: it models inter-slot dependency, which DSpark's Markov head
  already does (and vLLM's DSpark path already walks a top-k pruned Markov
  chain); stacking both needs a new loss and a separate serving path
  (vLLM's `dflash2` speculator), and the only prior art for conv + a
  Markov-style head reports +3.8%. Not worth a serving rewrite before the
  conv's own gain was known.
- *Loss / non-causal sliding*: kept DSpark's `0.1·CE + 0.9·TV` + confidence
  head so the run is a **one-variable ablation** against recipe A; the TV term
  is also what the confidence labels are defined on.

**Why conv first and from scratch**: it is orthogonal to the Markov head,
identity-init (a conv model loads a plain DSpark checkpoint with only conv
keys missing — warm-startable), intra-block (cannot reintroduce the
long-context decay the full-attention layers showed), and measurable on
train-side val accept_len before any serving work. We trained it **from
scratch with recipe A verbatim** (`run_nemo782k_conv_local.sh` /
`sbatch_sc3_nemo782k_conv.sh`: only `DSPARK_CONV_KERNEL=2 DSPARK_CONV_GROUP=16`
added; same data, schedule, seed) so the comparison is 1:1. The gate set in
advance: ≥ ~0.1 val accept_len over scratch before writing the serving patch.

Result: `gemma4_31b_dspark_nemo782k_conv/checkpoints/25` (= `checkpoint_best`),
val accept_len **4.779 vs 4.711** (+0.068 at matched epoch 25; +0.1…+0.15 at
epochs 17–23 while the scratch run was recovering from its warm restart).
Borderline on the gate; evaluated anyway — the benchmark gain turned out
larger than val suggested (§6). Trained on the sc3 cluster (job 11154700,
5 d 7 h on 8×B200, wandb `nemoconv782k_v2`).

**Serving a conv checkpoint** needs vLLM support that 0.26.0 lacks: the draft
is routed to `Qwen3DSparkModel` (`qwen3_dspark.py`) whose `load_weights`
silently drops the 20 conv tensors — the result loads and runs with the
convs missing. `vllm_patches/dflash2_conv.py` + `qwen3_dspark_conv.patch` +
`algos_conv.patch` (backport of vLLM main's `DFlashGroupedConv`; parity test
`test_dflash2_conv_parity.py`, exact vs the training conv) are applied in the
sc3 eval env; `sc3_eval_prelude.sh` refuses to serve a conv checkpoint on an
unpatched vLLM.

### 4.1 Block-size follow-up: block 12 by warm start

Nothing in a DSpark checkpoint has a block-size dimension (convs are
`[2, taps, hidden]`, the Markov head is `V × r`, no slot embeddings; RoPE
positions continue past the anchor), so a larger block can be trained from
the block-8 weights — the data layout (12 mask slots per anchor instead of 8),
the loss positions and the serve-time `k` are what change. We did that rather
than a from-scratch block-12 run (5.5 days) to get an answer in under 2.

| | `conv_blk12` (experiment) | `conv_blk8ctrl` (matched-exposure control) |
|---|---|---|
| seed | conv ep25 (`checkpoints/25`: weights + optimizer + scheduler state, copied into the new run dir; the trainer resumes from it) | same |
| block / γ | **12 / 12** (`BLOCK_SIZE=12 DECAY_GAMMA=12`) | 8 / 4 (the recipe's values) |
| epochs | 26 → 33 (**8 more**, `EPOCHS=34`) | same |
| schedule | linear, `SCHED_TOTAL=50600` (= 38,700 × 34/26, the budget of the whole 34-epoch trajectory): a warm restart with no new warmup: the resumed scheduler re-opened the LR at 1.6e-4 AdamW / 2.0e-3 Muon (the 6e-4 peak scaled by the budget left in the longer schedule) and decayed it linearly to 1.9e-5 / 1.9e-4 at the end of epoch 33 — not to 0, because both schedules are sized ~3% above the real step count (26 ep = 37.5k steps, not 38.7k), so the zero lies ~1.5k steps past the last step; the scratch and conv runs ended at the same floor | same |
| everything else | recipe B unchanged: nemo782k, ACCUM 18 × 4 ranks, `MAX_ANCHORS 512`, quarter-epoch saves | same |
| wrapper | `sbatch_sc3_conv_continue.sh` (8×B200, 4 HS engines + 4 ranks) | same |
| run | sc3-cp99, job 12398694, 2026-10-21 → 23, 1 d 15 h (~4.8 h/epoch), wandb `convblk12v1` | sc3-cp83, job 12398695, 2026-10-27 → 29 07:24, 1 d 15 h, wandb `convblk8ctrlv1` |
| val accept_len | 12-slot blocks: 5.15, 5.24, 5.29, 5.34, 5.35, 5.47, 5.49, **5.55** for epochs 26…33 | 8-slot blocks: 4.53, 4.57, 4.60, 4.64, 4.66, 4.72, 4.77, **4.81** for epochs 26…33 (conv ep25: 4.78 — the re-opened LR costs 0.25 at epoch 26 and the anneal wins it back, net **+0.03**) |

Why γ=12: the per-slot loss weight is `exp(−(k−1)/γ)`; at γ=4 the new slots
9–12 would get weights 0.14…0.06 and barely train, so the block-12 run uses
γ = block size (the paper's convention) while the control keeps the recipe's
γ=4 as a pure continuation. The val number is over 12 slots and is not
comparable to the block-8 runs' (4.78); it kept rising through the annealing
tail, which every run shows at the end of its schedule. The serve-time
verdict (k=12 vs k=8, same hardware) is in §6.3b: in-window acceptance
unchanged, +7…+16% tok/s on A100. Checkpoints:
`gemma4_31b_dspark_nemo782k_conv_blk12/checkpoints/{25..33}`
(`checkpoint_best → 33`); to serve at k=12 see §6.3b. Mechanics for any
further extension: resubmit the wrapper with a larger `EPOCHS` and a
recomputed `SCHED_TOTAL` (another warm restart), applied to both runs to keep
the exposure matched.

guaranteed rejection (~8% of the gap), the domain is intrinsically harder
(the assistant also drops 15% AIME → GPQA), and science is ~12% of the SFT
corpus vs 54% math (the remaining ~20%). Fixes in order of cost: larger draft
vocab; science-weighted on-policy data (OPD pool or SFT).
