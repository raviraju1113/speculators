# Qwen3.5 `l1234-v25` (One-Unified-SLM) speculative-decoding experiments

Results for the **`qwen35-l1234-v25-step6000`** target: its own trained MTP
module, two DSpark drafts, and the training-data thread that took a draft from
net-harmful to net-positive. Also four measurement bugs found here, each of
which had already corrupted published numbers (§5).

**Headline:** the target's own MTP head wins at **1.172×**. Our best
from-scratch DSpark draft reaches **1.074×** after the corpus was rebuilt from
real data; the same recipe on a synthetic corpus was **0.879×** — a net loss at
every depth.

All numbers here are from 2026-10-28/29 and carry the `enable_thinking=False`
fix (§5.1). **Every Qwen3.5 number measured before 2026-10-28 is invalid** and
is not reproduced in this doc.

---

## 0. The target

`/nvmedata/hf_checkpoints/qwen35-l1234-v25-step6000`

- Output of the One-Unified-SLM training run `l1234-v25`, best epoch 0,
  step 6000, PPL 1.337.
- 738 tensors. 15 `mtp.*` tensors live in a separate `model-mtp.safetensors`
  (241 MB).
- Nested config: `text_config` = hidden 2560, 32 layers, vocab 248320. No
  matching Qwen3.5 base on disk (2B = 2048/24, 9B = 4096/32, 27B = 5120/64).
- A JSON-extraction finetune. Correct output starts `{` and ends `}]}`; a
  response that reads like prose is a serving bug, not a model opinion.

**The MTP head is not the stock release head.** The checkpoint README states it
"includes the **trained MTP module**" and its blob path is
`..._ppl_1.337_trained_mtp/`. The head was trained *in the same run that
produced this target*, on that run's full data. So §3's MTP column is an
in-domain head co-trained with the target — not a vendor baseline. Any
comparison against it is a comparison against the strongest available
in-domain draft, and should be labelled that way.

## 1. Protocol

Identical for every arm in §3. The house rules in
[README.md](README.md) ("before quoting any number") are satisfied as noted.

| | |
|---|---|
| eval set | 2,000 prompts from `ChenWu/mai-profile-v2-slm`, `data/V2_User_Profile_L1_gpt56/test.jsonl` |
| decode | greedy — `temperature 0`, `top_p 1.0`, `top_k -1`, `max_tokens 8192` |
| chat template | `chat_template_kwargs={"enable_thinking": False}` — **mandatory**, see §5.1 |
| concurrency | 32 |
| serving | vLLM **0.31.0** (`/nvmedata/chenw/envs/speculator-vllm031`), tp=1, single GPU |
| prefix caching | **off** (`enable_prefix_caching=False`) on all 14 arms — house rule 1 |
| co-tenancy | arms run **serially on GPU 0**, one server per arm — house rule 2 |
| training | HS server on vLLM **0.24.0** (`speculator` conda env) |
| harness | `qwen35_mtp_sweep.py`, AL/AR read from vLLM's own Prometheus counters |

**Cross-run comparison is justified here, not assumed.** §3's two halves ran
four hours apart in separate sessions, which house rule 2 forbids by default.
Both halves therefore carry their own independently launched baseline arm, and
the two agree to **0.15%** (1572.9 vs 1570.5 tok/s; 1.225 vs 1.222 req/s).
That matched control is what licenses reading the two halves as one table.

### Metrics

- **AL** (accept length) = `1 + accepted/drafts`. Tokens committed per target
  forward pass, max `k+1`.
- **AR** (accept rate) = `accepted/draft_tokens`. Depth-normalised, so it
  **falls as k rises by construction** — never compare AR across different k.
- **AR@pos** = `num_accepted_tokens_per_pos[pos] / num_drafts`, vLLM's own
  formula (`v1/spec_decode/metrics.py:194`). The counter increments once per
  draft reaching that depth, so this is a **survival curve**: monotonically
  non-increasing, and `AL = 1 + Σ AR@pos` is an exact cross-check. It holds on
  all 12 speculative arms below.
- **speedup** = **req/s** ratio against the baseline arm, *not* tok/s. When
  arms differ in output length, tok/s rewards a draft for making responses
  longer while the user waits longer. Here the two happen to agree (§4.4), but
  req/s is the honest headline and is what the table reports.
- **dtok / longer% / ident% / div@** — paired per-prompt against the baseline:
  median token delta, share of prompts whose response got longer, share
  byte-identical, and median index of the first differing character. Added for
  the 2026-10-28 MTP sync; read §4.3 before using any of them.

## 2. The training corpus

The goal was a corpus matching the finetuned target's own distribution.

**Source:** `ChenWu/mai-profile-v2-slm`, subset `V2_User_Profile_L1_gpt56`,
train split (267,810 rows; 1,758,247 across all 16 L1–L4 splits).

**Build:** 20,000 train + 2,000 val prompts, responses **regenerated by the
target itself** (greedy, `enable_thinking=False`). The shipped assistant turns
are GPT-5.6 text and are discarded: acceptance measures agreement with the
*target's* argmax, so the target's own output is the only correct label.

**Verified by prompt hash before training:**

| | n | in HF train split | in eval set |
|---|--:|--:|--:|
| regen input, train | 20,000 | 20,000 (100%) | 0 |
| regen input, val | 2,000 | 2,000 (100%) | 0 |
| regen output, train | 20,000 | 20,000 (100%) | 0 |
| regen output, val | 2,000 | 2,000 (100%) | 0 |

Train/val prompt overlap: 0.

**Split by uid group, not by row.** `uid` is not unique — a user contributes
several activity windows, median 12 rows/uid. A row split puts the same user on
both sides of the boundary. (Caught by an assertion, not by inspection.)

**Prepared:** 15,579 train + 1,582 val = 17,161 rows at `--seq-length 8192`,
`--minimum-valid-tokens 32`. 22% dropped in preprocessing, evenly across both
sides — length filtering, not a split artefact.

Scale caveat for every conclusion below: **15,579 rows is ~1.1% of one L1
subset**, 0.9% of the 1.76M available. MTP's head saw the full `l1234-v25`
pipeline.

### 2.1 Training

1h38m on 3 GPUs (HS server on the 4th), 2 epochs, `--speculator-type dspark`
warm-started from `output/dspark_from_dflash_init_qwen35`,
`--target-layer-ids 2 6 10 14 18 22 26 30`, `--total-seq-len 8192`,
`--loss-fn '{"ce":0.1,"tv":0.9}'`, lr 1e-4. Train loss 0.65 → 0.137.
`checkpoint_best` → epoch 1.

Validation on the 1,582 genuinely held-out rows:

| pos | 1 | 2 | 3 | 4 | 5 | 6 | 7 | 15 |
|---|--:|--:|--:|--:|--:|--:|--:|--:|
| acc | **.915** | .889 | .866 | .847 | .830 | .816 | .803 | .721 |

## 4. Findings

### 4.1 The corpus was the problem, and real data fixed it

AR@1 by corpus, same recipe, same target, same protocol:

| corpus | AR@1 | best speedup |
|---|--:|--:|
| general-purpose (off-domain) | .694 | 0.839× |
| fabricated in-format (§3.1) | .754 | 0.879× |
| **real HF rows, target-regenerated** | **.869** | **1.074×** |

Fabricating prompts in the eval's exact *format* bought 6 points of AR@1 over
an off-domain corpus and still lost to the baseline at every depth. Using the
*real rows* bought 17.5 points and crossed into net gain at k=3.

Format-matching is not distribution-matching. The fabricated corpus passed a
gate comparing its response-length distribution and `starts-with-{` rate
against the eval set, and that gate was satisfied while the corpus was still
wrong enough to make the draft harmful.

### 4.2 Validation is now predictive of serving — the actual diagnostic

`val/position_1_acc` and served `AR@1` both mean "first draft token accepted",
so they are directly comparable.

| run | val pos1 | served AR@1 | gap |
|---|--:|--:|--:|
| synthetic (job 373) | .945 | .754 | **19.1 pt** |
| real data (job 376b) | .915 | .869 | **4.6 pt** |

Job 373 had **no `--val-data-path`**, so its validation split was carved from
the same 19,990 synthetic rows it trained on. It reported .945 and served .754.
The clean run reports a *lower* .915 and serves .869.

A 19-point train/serve gap is the signature of a corpus the target never sees.
It was visible in job 373's own logs before any serving run, and is the cheapest
available check on a new corpus — it costs nothing and it caught this.

**Do not compare `val/position_k_acc` to `AR@pos` beyond position 1.** Val
accuracy is conditional on a teacher-forced correct prefix; `AR@pos` is a
survival curve. Chaining the val curve gives `AL ≈ 5.2` at k=7, which serving
does not reach (4.359) and was never going to.

### 4.3 The target is non-deterministic under greedy decoding

`baseline_B` is a second run of the baseline at byte-identical settings:

- **684 / 2000 responses byte-identical — 1,316 differ**
- 1,234 rows differ in token count; **max per-request delta 6,219 tokens**
- median first divergence at character 1,092

Mechanism: at concurrency 32 the batch a request lands in varies between runs,
changing matmul reduction order. This reproduces in both halves of §3
(`ident%` 34.2 and 33.8).

Two consequences, both load-bearing:

1. **Output divergence cannot be attributed to speculative decoding on this
   setup.** Every speculative arm's `ident%` (30.6–32.9%) is statistically
   indistinguishable from the baseline-against-baseline control (33.8–34.2%).
2. **Losslessness cannot be verified by output identity here.** Under greedy,
   lossless speculation should be output-identical to the no-draft baseline —
   but the baseline is not identical to itself, so the check has no power. A
   different method is needed to confirm losslessness on this target.

### 4.4 Output-length inflation does not reproduce

The 2026-10-28 sync recorded drafts generating "significantly longer
responses — such as 50 tokens instead of 10". On this workload, at n=2000:

| arm | mean tok | p50 | p90 |
|---|--:|--:|--:|
| baseline | 1284.0 | 818 | 3197 |
| baseline_B (control) | 1287.6 | 816 | 3181 |
| MTP k=5 | 1286.0 | 816 | 3159 |

Within **0.3%**. `tok p50` is 814–819 across all 14 arms. The largest median
`dtok` is +10.7 on a median of 816, and the control run drifts +3.6 by itself.

So the effect is **not present here above the target's own run-to-run noise**.
This does not refute the original observation — different workload, and a
JSON-extraction target has little room to ramble. What it does establish is the
method: **any future measurement of output-length inflation needs a second
baseline arm**, or §4.3's non-determinism will be misread as a
speculative-decoding effect.

### 4.5 MTP wins on acceptance quality, not on overhead

1.172× vs 1.074×. Implied draft overhead is nearly identical — from
`speedup = AL/(1+Ω)` at k=5, Ω ≈ 2.61 (MTP) vs 2.70 (ours) — so DSpark's
separate 4.07 GB model is *not* what costs it. MTP simply predicts better at
every depth and the advantage compounds through the survival curve: .303 vs
.220 of drafts still alive at depth 7.

This is the opposite of the Gemma-4-26B finding (26B doc §15), where acceptance
was near-identical across drafts and Ω decided the ordering. Here Ω is
near-identical and acceptance decides it.

Given §2's scale caveat — 1.1% of one subset against a head co-trained on the
full pipeline — a .869 vs .901 acceptance gap reads as a **data-scale** gap,
not an architecture gap. That is the next experiment, not a conclusion.

### 4.6 k=1 always loses

0.871× (MTP) and 0.739× (ours), despite both having their highest AR at k=1.
One accepted token does not repay one draft forward pass. Both curves peak
late: MTP at k=5, ours at k=7.

## 5. Bugs found here

Each of these had already produced numbers that were reported or acted on.

### 5.1 `enable_thinking` — invalidates every pre-2026-10-28 Qwen3.5 number

The target's chat template leaves a `<think>` block open under
`add_generation_prompt`, and the model then answers mid-string: **0/2000 valid
JSON** by default, 2000/2000 with `chat_template_kwargs={"enable_thinking":
False}`. Baseline tok/req was 2231.0 in the broken mode vs 1286.2 fixed —
runaway generations inflating throughput for every arm.

Every Qwen3.5 measurement before 2026-10-28 was taken in that mode and is not
comparable to anything in this doc. The harness now takes `--no-thinking` and
records `valid_pct` per arm so a target emitting 0% valid JSON cannot go
unnoticed again — which it did, for weeks.

### 5.2 Validation carved from the training rows

See §4.2. No `--val-data-path` → `train_data_ratio` splits one dataset
**positionally** (`src/speculators/train/data.py:227`). Fixed by preparing train
and val separately and computing an exact boundary.

Two traps in that fix, both of which silently reproduce the original bug:

- `prepare_data` **shuffles twice and drops rows**
  (`raw_dataset.shuffle(seed)`, then `combined_dataset.shuffle(seed)` after
  `concatenate_datasets`). A positional boundary therefore **cannot** be built
  by concatenating jsonl files first.
- The ratio must be validated as the **rounded string** the trainer parses, not
  as a full-precision float: `int(total * float("%.10f" % r))` can land a row
  off. The builder searches for a string that produces the exact intended
  `split_idx` and refuses to train if it cannot find one.

### 5.3 AR@pos shifted by k positions

`prometheus_client` emits a `_created` series beside every `_total` counter. Its
value is a fixed creation timestamp, so its after-minus-before delta is 0 — and
`"created"` sorts before `"total"`. Scraping both prepended **k spurious zeros**
to every per-position curve, so each depth label was shifted by k: a k=1 arm
reported `@1=0.000, @2=0.901`.

`AL` and `AR` were never affected, which `AL == AL_chk` on all 12 arms
independently confirms. Positions are `range(num_speculative_tokens)` in both
vLLM 0.24.0 and 0.31.0 (`v1/spec_decode/metrics.py:261`) — exactly k series per
engine, so any curve longer than k is an artefact.

An earlier version of the same scrape summed *over* the `position` label and
discarded the curve entirely, so AR@pos did not exist at all.

### 5.4 HS server without `--speculative_config` (cost one full run)

`ExampleHiddenStatesConnector` asserts that `speculative_config` is set and its
method is `extract_hidden_states`
(`vllm/distributed/kv_transfer/kv_connector/v1/example_hidden_states_connector.py:138`).
Launched without it, the engine core dies at KV-connector init, `:8003` never
binds, and training aborts — after `prepare_data` has already run.

The flag also needs **nine** `eagle_aux_hidden_state_layer_ids`
(`[2,6,10,14,18,22,26,30,32]`) for **eight** `--target-layer-ids`: the server's
last id is the final hidden state, so it returns `len(ids)-1` aux tensors.
Eight ids yield 7×2560 against the draft's 8×2560 `fc` and training dies on
"a and b must have same reduction dim".

### 5.5 Two corpus-truncation bugs (training data only)

- **Regen context.** `--max-model-len 16384` with `--max-tokens 8192` rejects
  every prompt over 8192 tokens — 245/2000 val rows (12.2%), median 25,048 user
  chars against 3,758 for kept rows. The eval server uses 32768. A corpus built
  this way is silently length-biased toward short prompts. Fixed to 32768; a
  drop-rate guard now aborts the build if any shard keeps under 98% of its rows.
- **`--total-seq-len`.** At 4096, 12.6% of real rows lose the assistant
  response entirely and only 52.5% of response tokens survive (job 373's prep
  log: 4,521/19,990 rows with "No assistant response spans found"). At 8192: 0%
  and 83.2%.

## 7. Where the draft's weight and its cost actually go (2026-10-30)

Four findings (§7.1–§7.4) established by reading the checkpoints and the engine
logs rather than by training anything, plus a cost decomposition of §3's sweep
(§7.5–§7.6). No new GPU time. Together they close two proposed optimisations as
dead ends and re-aim §6 at the only axis that is still open.

### 7.1 The draft's live weight is not its file size

`output/realdata_qwen35/checkpoints/1/model.safetensors` is 75 tensors,
2,032,966,913 params, **4.07 GB** on disk (3.79 GiB). Two of those tensors are
the vocabulary:

| tensor | shape | dtype | sha256 (raw blob) |
|---|---|---|---|
| draft `embed_tokens.weight` | (248320, 2560) | BF16 | `23d97baf855ddec8…` |
| draft `lm_head.weight` | (248320, 2560) | BF16 | `23d97baf855ddec8…` |
| target `model.language_model.embed_tokens.weight` | (248320, 2560) | BF16 | `23d97baf855ddec8…` |

**All three blobs are bit-identical** — same 1,271,398,400 bytes, same digest.
The target carries `tie_word_embeddings: true` and ships no `lm_head` at all, so
one matrix serves as the target's input embedding, the target's output head, and
both of the draft's copies.

vLLM already exploits this. `_should_share`
(`v1/worker/gpu/spec_decode/eagle/utils.py:15`) compares the candidate weight
against the target's with `torch.equal`; on a match the caller does
`del draft_inner.embed_tokens` / `del eagle_model.lm_head` and rebinds the
draft's attribute to the *target's* module. So 1271.4M of the draft's params —
**2.54 GB, 62.5% of the file** — are read off disk and then dropped.

| component | params | bf16 |
|---|--:|--:|
| `embed_tokens` + `lm_head` — shared away | 1271.4M | 2.54 GB |
| 6 decoder layers + norms + confidence head | 582.0M | 1.16 GB |
| `markov_head.markov_w1` | 63.6M | 0.13 GB |
| `markov_head.markov_w2` | 63.6M | 0.13 GB |
| `fc` | 52.4M | 0.10 GB |
| **live draft weight** | **761.6M** | **1.52 GB** |
| file on disk | 2033.0M | 4.07 GB |

The engine logs agree without being asked. In job 377, same GPU, same session:
`Model loading took 8.61 GiB` with no draft and `10.21 GiB` with the k=7 draft
attached — a **marginal 1.60 GiB** against the 3.79 GiB the file would imply and
against 1.419 GiB of computed live weight. The 0.18 GiB remainder is engine
scaffolding, not vocabulary.

**Consequence for §4.5.** "DSpark's separate 4.07 GB model" was never 4.07 GB at
serving time. Of the three remaining heads, `fc` and the two Markov factors are
0.36 GB combined; the body is the rest.

### 7.2 The MTP baseline is a one-layer head

`model-mtp.safetensors` in the target directory is 15 tensors, 120,599,552
params, **0.24 GB**:

| tensor | shape | params |
|---|---|--:|
| `mtp.layers.0.mlp.{gate,up}_proj.weight` | (9216, 2560) | 23.6M each |
| `mtp.layers.0.mlp.down_proj.weight` | (2560, 9216) | 23.6M |
| `mtp.layers.0.self_attn.q_proj.weight` | (8192, 2560) | 21.0M |
| `mtp.layers.0.self_attn.o_proj.weight` | (2560, 4096) | 10.5M |
| `mtp.layers.0.self_attn.{k,v}_proj.weight` | (1024, 2560) | 2.6M each |
| `mtp.fc.weight` | (2560, 5120) | 13.1M |
| 7 norms (`input`, `post_attention`, `q`, `k`, `mtp.norm`, 2 × `pre_fc_norm`) | | 0.013M |

One decoder layer — `mtp.layers.0.*` and nothing else, matching the target
config's `mtp_num_hidden_layers: 1`. **No `lm_head`, no `embed_tokens`**, so by
§7.1's mechanism it shares the target's too; 120.6M is both its file size and
its live weight.

Two shapes carry the architectural difference:

- `mtp.fc.weight` is (2560, **5120**) — its `fc` consumes **two** 2560-wide
  inputs.
- our `fc.weight` is (2560, **20480**) — **eight** aux hidden states, which is
  `--target-layer-ids 2 6 10 14 18 22 26 30` (§2.1).

So our draft carries **6.31× MTP's live weight** (761.6M vs 120.6M) and **six
layers against its one**, and has lower acceptance at every depth (§3). Note the
6.31× is not fatter layers: one MTP layer is 107.5M against 97.0M for one of
ours, because the target's own attention is 8192-wide where the draft's is 4096.
The ratio is layer *count* plus the Markov and `fc` heads.

**That is a data deficit, not a capacity deficit.** The supporting fact is in the
target's own README: the MTP module was trained *inside* the full `l1234-v25`
SLM run — best epoch 0, step 6000, PPL 1.337, "includes the trained MTP module"
— on that run's entire training mixture. Our draft saw 15,579 rows for 2 epochs
(§2). A 6× larger head losing to a 1-layer one is what a 1.1%-of-one-subset
corpus looks like, and it is the same reading §4.5 reached from the survival
curve alone.

### 7.3 E1 — stripping `embed_tokens` from the draft is a confirmed no-op

`output/realdata_qwen35/checkpoints/best_noembed` is checkpoint 1 with
`embed_tokens.weight` removed: 74 tensors, 1,397,267,713 params, **2.79 GB**
against 4.07 GB — exactly the 1.27 GB that tensor occupies.

Job 377 (`results/qwen35-noembed`) serves both drafts in one session, same GPU,
same flags, k=7. The engine's memory accounting is **identical to the digit**:

| | `e_orig_k7` (4.07 GB draft) | `e_noembed_k7` (2.79 GB draft) |
|---|---|---|
| Model loading took | 10.21 GiB | 10.21 GiB |
| Available KV cache memory | 58.14 GiB | 58.14 GiB |
| GPU KV cache size | 1,110,643 tokens | 1,110,643 tokens |
| max concurrency @ 32,768 | 33.89× | 33.89× |
| weight-load wall time | 5.815 s | 5.854 s |

**Explained entirely by §7.1: vLLM was already freeing that tensor.** Stripping
it changes what is read from disk, not what is resident. There is no KV-cache
headroom to win because none was being lost.

E1's benefit is therefore **1.27 GB of disk and nothing else**. The load-time
argument does not survive either: the stripped draft loaded 0.04 s *slower* in
this pair, so at this file size the difference is below measurement noise.
**Record E1 as a negative result.**

**The unstripped arm reproduced byte-for-byte across sessions.** `e_orig_k7` and

### 7.4 Rejected: pruning `draft_vocab_size`

The proposal was a mapped draft vocabulary — `draft_vocab_size=32768` instead of
248,320 — to shrink the draft's head. §7.1 makes it **strictly negative**:

1. **It costs resident memory that is currently free.** The full-size
   `lm_head` is bit-identical to the target's, so `_should_share` returns True
   and it occupies **zero** GPU bytes. A pruned head is not bit-identical,
   `torch.equal` returns False, and vLLM must allocate it:
   32,768 × 2,560 × 2 B = **167.8 MB (160.0 MiB) of new resident weight**. The
   pruning direction is backwards — the thing it would shrink is the one part of
   the draft that is already free.
2. **It costs acceptance.** Over the 20,000 target-regenerated train responses
   (`output/realdata_qwen35/real_train.jsonl`, 27,185,332 response tokens):

   | | value |
   |---|--:|
   | distinct response token ids | 59,296 |
   | as share of the 248,320 vocab | 23.88% |
   | covered by the top 32,768 by frequency | **99.578%** |
   | **predict-miss at 32,768** | **0.422%** |

   A token outside the map cannot be drafted at all, so that 0.42% is a floor on
   lost first-position acceptance, paid on top of the 167.8 MB.

**Rejected.** This is the Gemma-4-26B result reached from the other direction:
26B doc §31.2 trained a 32,000-entry draft and measured −1.33 AL and −22%
throughput against the full 262k head. Here the arithmetic rules it out before
any GPU time is spent.

### 7.5 Cost decomposition: our per-draft-token cost is already lower than MTP's

§4.5 computed implied overhead at k=5 only. Fitting it across the whole sweep
changes the conclusion. Write `speedup(k) = AL(k) / D(k)`, so the measured
denominator is `D(k) = AL(k)/speedup(k)` — target forward passes' worth of work
per committed group, `D = 1 + Ω` in §4.5's notation. From the raw arms, n=2000,
greedy, concurrency 32, vLLM 0.31.0, prefix caching off, serialised on one GPU:

| k | MTP AL | MTP speedup | MTP D | ours AL | ours speedup | ours D |
|--:|--:|--:|--:|--:|--:|--:|
| 1 | 1.901 | 0.8706× | 2.183 | 1.869 | 0.7389× | 2.530 |
| 2 | 2.672 | 1.0265× | 2.603 | 2.587 | 0.9069× | 2.852 |
| 3 | 3.299 | 1.1434× | 2.885 | 3.165 | 1.0202× | 3.103 |
| 5 | 4.231 | 1.1718× | 3.610 | 3.945 | 1.0670× | 3.697 |
| 7 | 4.826 | 1.1708× | 4.122 | 4.359 | 1.0739× | 4.059 |

MTP from `results/qwen35-postfix-mtp` against `p_baseline` = 1.2250 req/s; ours
from `results/qwen35-realdata-greedy` against `r_baseline` = 1.2225 req/s. Each
arm is scored against its own run's baseline, and the two baselines agree to
0.2% (§1).

Least squares on `D(k) = 1 + fixed + k × per_token`:

| | fixed | per_token | rms resid |
|---|--:|--:|--:|
| MTP | 0.917 | **0.323** | 0.053 |
| ours | 1.321 | **0.258** | 0.054 |

**Our marginal cost per draft token is 20% lower than MTP's.** The mechanism is
in the method: we draft a block (`block_size: 16`, §2.1 / DSpark), so extra
depth is mostly the target verifying k+1 positions instead of k, whereas MTP
additionally pays **k sequential passes of its head**, one per position. We pay
for that with a larger fixed term — the 6-layer body and the 8-way `fc` have to
run once whatever k is.

The two lines cross at **k ≈ 6.16**, and the measurement has already passed it:
at k=7 our D is **4.059 against MTP's 4.122**. We are the cheaper draft at the
depth both curves are actually served at.

**So at depth we have no cost problem; the whole remaining deficit is AL** —
4.359 against 4.826. Concretely, to reach MTP's best 1.172× at our *existing*
k=7 cost we need

```
AL ≥ 1.1718 × 4.0595 = 4.757
```

which is **below MTP's own k=7 AL of 4.826**. The target is not "beat the best
head on its own terms"; it is "match what that head already does at depth 7,
while paying less per token than it does". That is §6's corpus scale-up, and
§7.2 is the reason to expect data to deliver it.

### 7.6 A 3-layer body looked cheaper — on a run §5.1 invalidates

There is a pre-existing 3-layer-vs-6-layer comparison in
`results/qwen35-full-greedy`. **It cannot be used, and the reason is this doc's
own §5.1.** Checked before quoting it:

- The run is dated **2026-10-26/27**, before the `enable_thinking=False` fix.
- Every one of its 23 arms reports **2,180–2,303 tok/req** with ~12% of requests
  (240–270 of 2,000) hitting the `max_tokens` cap. §5.1's signature for the

- The harness predates the validity instrumentation, so no `valid_pct` was

- Its drafts are also a different lineage: `output/onpolicy_qwen35/checkpoints`

So this is a measurement of a serving mode that emits no valid JSON, and the

re-test, not as evidence.** For the record, what it measured — scored within-run

|---|--:|--:|--:|
| 3-layer body | 3.713 | 3.758 | 0.9880× |

Halving the body cut the denominator 0.305 and cost 0.177 AL, net +3.2%; and at

## 8. Depth is exhausted; the gap is the survival curve (2026-10-30, job 379)

### 8.1 Raising k loses, as predicted

§7.5 predicted this before the run: measured marginal cost was 0.258 per draft
token while extrapolated marginal survival was only S8~.172 and S9~.133, so AL
should rise while speedup FALLS. Job 379, six arms against its own baseline,
`results/qwen35-kdepth`:

| arm | AL | speedup | D = AL/speedup |
|---|---|---|---|
| n_k7 | 4.359 | **1.0830x** | 4.025 |
| n_k9 | 4.603 | 1.0203x | 4.511 |
| n_k11 | 4.791 | 0.9937x | 4.822 |

AL rises monotonically, speedup falls monotonically, and k=11 is slower than
not drafting at all. The extrapolation was accurate to 0.002 at both probe
positions (measured S8 .170, S9 .135). **k=7 is the ceiling. Raising k is
closed**, and no future arm should spend GPU time re-testing it.

### 8.2 Adaptive verification is impossible on this target

Both `enable_adaptive_verification` arms failed at server start:

```
ValueError: Adaptive verification trims verification requests on device, which
the GDNAttentionBackend attention backend does not support. Pass
enable_adaptive_verification=false in the speculative config, or use a backend
that does.
```

`adaptive_verification.py:472` rejects any target whose attention backends
cannot tolerate a query-length mismatch, and only FlashInfer advertises support
(`flashinfer.py:1068-1074`). This target is hybrid — `layer_types` is 24
`linear_attention` + 8 `full_attention` (§0) — and the Gated DeltaNet layers
cannot. No flag routes around a backend the model's own layers require. This
closes the one remaining idea from the tree-drafting survey; it is a property
of Qwen3.5's architecture, not of our checkpoint.

### 8.3 Cost structure: we win on the margin, lose on the fixed term

D fitted as `D(k) = 1 + fixed + k*per_token`, each arm against the baseline of
its own run (house rule), ours over k=1..7 from `qwen35-realdata-greedy` and
MTP over k=1..7 from `qwen35-postfix-mtp`:

| | fixed | per_token (k=5->7) | D(7) | live weight |
|---|---|---|---|---|
| MTP, 1 layer | **0.918** | 0.256 | 4.122 | 120.6M |
| ours, 6 layers | **1.321** | 0.181 | 4.059 | 761.6M |

Our *marginal* cost is substantially better — the single batched non-causal
forward does what §7.6 said it would. We lose on the **fixed** term: the draft
machinery costs 1.32 target-forwards before it drafts a single token. The 0.403
gap is ~5 extra layers at ~0.08 each, which is self-consistent with MTP being
exactly one layer.

At our measured marginal cost of 0.181, `speedup(7) = AL / (1 + fixed + 7*0.181)`:

| | fixed 0.92 | 1.05 | 1.20 | 1.32 (today) |
|---|---|---|---|---|
| AL 4.359 (today) | 1.369x | 1.315x | 1.258x | 1.216x |
| AL 3.900 | 1.225x | 1.177x | 1.126x | 1.088x |
| AL 3.700 | 1.162x | 1.116x | 1.068x | 1.032x |

**A draft with MTP's fixed term beats MTP's 1.172x at any AL >= 3.74.** We are
at 4.359, so there is a ~14% AL budget to spend buying the fixed term down.
This is the first design on the table with real headroom, and it runs against
the instinct to add capacity: our 6.3x weight advantage buys no AL (we lose to
a one-layer head) and costs 0.40 in fixed D.

### 8.4 Where the AL gap actually is

Survival and per-step conditionals `c_j = S_j / S_{j-1}` at k=7:

| pos | 1 | 2 | 3 | 4 | 5 | 6 | 7 | AL |
|---|---|---|---|---|---|---|---|---|
| MTP survival | .858 | .719 | .608 | .520 | .447 | .371 | .303 | 4.826 |
| ours survival | .828 | .684 | .560 | .440 | .350 | .277 | .220 | 4.359 |
| MTP conditional | .858 | .838 | .846 | .855 | .860 | .830 | .817 | |
| our conditional | .828 | .826 | .818 | .786 | .795 | .791 | .794 | |

MTP's per-step conditional is flat at .82-.86; ours decays and sags worst at
positions 4-5. Decomposing the 0.467 AL gap: holding our position-1 rate (.828)
at every step with no decay would give AL 4.530, so **intra-block chain decay
is 0.171 (37%) and a uniform per-step accuracy deficit is 0.296 (63%)**. An
earlier draft of this analysis attributed ~73% to the chain; that was
arithmetically true of "positions 2+" but misleading, because a uniform
per-step deficit also compounds into positions 2+.

The mechanism is in the serving code, not inferred. `DSparkSpeculator.
_generate_draft` makes exactly one `self.model(...)` call, CUDA-graph captured
end to end, and the class docstring states the Markov head adds "a
prefix-dependent Markov bias derived from the previously sampled token":
position j's hidden state never sees tokens 1..j-1, only its logits are nudged.
**Block chaining does not exist** and would be a vLLM change, not a flag.

That also caps what chaining is worth. At our measured D(7)=4.025:

| | AL | speedup |
|---|---|---|
| measured k=7 | 4.359 | 1.083x |
| + a perfect chain | 4.530 | 1.125x |
| + MTP's per-step rate too | 4.826 | 1.199x |
| MTP measured (its own D 4.118) | 4.826 | 1.172x |

A perfect chain alone lands at 1.125x, **still short of MTP**. Only fixing the
per-step term as well wins, and the largest AL movement ever measured on this
target came from data: the synthetic-corpus draft scored AL 2.825 at k=7
(`p_gen_dspark_k7`), the same architecture on 15,579 real rows scored 4.359.
Nothing architectural has moved AL by a fraction of that.

### 8.5 Two bugs in the init builders

**`rope_theta` was silently defaulted.** `build_dspark_init_qwen35.py:76` reads
`dfl_cfg.get("rope_theta", 1000000)`, but the DFlash stores it as
`rope_parameters.rope_theta = 10000000`, so the `.get` misses and takes the
fallback. The target is 1e7 and the pretrained DFlash is 1e7, so the
warm-started attention was **pretrained at 1e7 and then fine-tuned at 1e6** —
the mismatch corrupted the warm start, not just the agreement with the target.
`build_init_qwen35_3layer.py` reads `dfl.get("rope_parameters", {}).get(...)`
and is correct. Note the 1e6 is explicit in the checkpoint config, so vLLM's
`set_default_rope_theta` never fired; that function only fills a MISSING key
(`transformers_utils/config.py:587`), which also means a corrected 1e7 survives
to serve time and introduces no train/serve mismatch.

**"RMSNorms are exactly 1.0" is not evidence of a random init.** An earlier
check concluded the draft body was randomly initialized because every
`input_layernorm.weight` has mean 1.0000. The pretrained DFlash has mean 1.0000
too, so the signal is worthless. Bit-identity settles it: all 11 tensors of
DFlash layer 5 are `torch.equal` to the live init's layer 5, and to
`e3_init_1layer_full`'s layer 0. **The live draft is genuinely warm-started.**
The three config-only `e3_init_3layer_*` checkpoints are still random (body std
0.0200 = `initializer_range`, with no copy step), so they remain confounded
against the live baseline on rope base, init scale and init provenance.
